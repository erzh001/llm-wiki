# Vault template — папка как точка входа + скелет project-vault

**База-баз** того, как устроена папка домена и её vault. Домены (`study`,
`creative`, …) соответствуют этому шаблону и записывают только свои **дельты**
в собственной `principles.md`. Правила письма на уровне объектов — в
[[meta-vault/principles|principles]]; этот файл — **структура + контракт точек
входа**.

## Модель — точка входа это папка

Папка домена — это **не** только её vault. В ней живут vault (база знаний)
**плюс** код-проекты, доки, агентские файлы, презентации — что угодно. Когда
агент открывает папку как cwd, он должен с первой попытки: понять, что это за
место, найти vault и найти каждый проект внутри.

```
<домен>/                     ← ТОЧКА ВХОДА (папка, открываемая как cwd)
  CLAUDE.md        [door]     ← авто-грузится харнессом. Манифест.
  README.md        [human]    ← опционально, только людям, не несёт маршрутизации
  <проект-1>/ CLAUDE.md       ← у каждого код-репо своя дверь
  <проект-2>/ …
  docs/ presentations/ …      ← прочее содержимое — перечислено в двери
  <домен>-vault/              ← база знаний
    HOME.md        [map]      ← семантическая навигация по знанию
    status.md      [hot]      ← текущее состояние, читается каждую сессию
    principles.md  [rules]    ← «следует базе + эти дельты»
    market/ plans/ tasks/ …   ← канонические зоны (ниже)
```

## Контракт точек входа

**Цепочка: `[door]` → `HOME.md` (карта) → знание.** Одна роль на файл;
**имя двери зависит от харнесса**.

- **Дверь.** Харнесс **авто-грузит** её от cwd вверх по родителям; больше ничего
  не авто-грузится. Имя файла зависит от инструмента: **`CLAUDE.md`** (Claude
  Code), **`AGENTS.md`** (Codex и другие). Папка, используемая несколькими
  инструментами, несёт **оба файла как синхронные по содержанию твины**
  (различается только слово-имя инструмента) — это правильно для цели
  LLM-независимости, а *не* дубликат на удаление. Обязательна в каждом
  открываемом cwd: корень каждого домена **и** каждый код-репо. Дверь — это
  **манифест**: (а) что это за место, (б) маршрут сначала в vault (`HOME.md` +
  `status.md`), (в) **перечисление проектов/зон внутри**, чтобы агент нашёл всё
  с первой попытки. Тонкая и стабильная. Образец двери: [[study/CLAUDE|дверь study]].
- **`HOME.md` — карта.** Достигается *через* дверь (никогда не авто-грузится).
  Ровно одна на корень vault. Семантическая навигация по темам. **Не**
  дублировать её в корне рабочей папки — карта живёт в vault.
- **`README.md` — людям.** Опционально. Никогда не класть агентскую
  маршрутизацию только в README — харнесс его не открывает: правда, живущая в
  файле, который машина не грузит, для агента не существует.
- Папка, являющаяся только базой знаний (без кода), всё равно получает дверь
  `CLAUDE.md`, если может быть открыта как cwd; допустим однострочный редирект
  в `HOME.md`.

## Скелет project-vault

`<домен>-vault/`. **Обязательный** хребет + **общее** тело + **опциональное**
по типу деятельности. Каждая зона — один-файл-на-объект по
[[meta-vault/principles|principles]].

**Обязательное**
- `HOME.md` [map], `status.md` [hot], `principles.md` [rules],
  `secrets-map.md` (указатели).
- `market/` — `overview.md` + `competitors/` (один файл на конкурента).
- `plans/` — открытые роадмапы + горизонт (`vision` / `now`); дифференциальны,
  пересобираются от состояния.
- `tasks/` — run-данные агентских циклов (`spec → plan → build → review →
  record`).

**Общее тело**
- `systems/` — собственные компоненты (что это и зачем, не имплементация).
- `decisions/` — датированные прецеденты `YYYY-MM-DD-*` (включая негативные
  «отвергли X»).
- `lessons/` — операционные правила (триггер → правило → почему).
- `tools/`, `people/` — справочные карточки.
- `_archive/` — терминальная зона; живых ссылок из канона нет.

**Опциональное по типу деятельности**
- `clients/` — если клиентский бизнес.
- `analytics/` — количественный анализ продукта.
- `research/` — длинные разборы с TL;DR.
- `positioning.md` — если есть внешнее предложение.
- `curriculum/` — если образовательная деятельность.

## Контракт status.md — блокеры видны с самого верха

`status.md` — **горячее состояние**, читается каждую сессию. Правило записи:
**блокеры должны быть видны высокоуровневому агенту без закапывания в
боковые доки.**

- **Вести поверхность `Blockers` / «не сделано» — первой, не хоронить.** Прямо
  писать, что **не** сделано и что чем гейтится. Реальный блокер, лежащий в
  `docs/*.md`, невидим планирующему агенту, который читает только дверь +
  `status.md`. (Тот же класс бага, что маршрутизация в README: правда есть, но
  в файле, который машина не авто-открывает.)
- **«Задеплоено / работает» ≠ готово — витринный вид прячет последнюю милю.**
  Статус, начинающийся с успеха, делает высокоуровневое чтение уверенно
  неправым на финальном шаге. Всегда парой: *что работает* + *что блокировано*.
- **Кросс-доменные блокеры поднимать ВВЕРХ.** Блокер, гейтящий приоритет
  верхнего уровня, копируется в **hot-state, который верхний уровень реально
  читает**, с **конкретным** блокером, а не расплывчатым «есть гейт». Top-агент
  должен наткнуться на него при обычном чтении.
- **Когда обновлять** — в конце каждой сессии, где менялись файлы уровня:
  ритуал — [[meta-vault/session-close|session-close]].
- **Почему это важно (принцип):** планирование **двухвысотное** — верх владеет
  приоритетом, проект владеет реальными блокерами; корректность приходит из
  правильных *данных* (честный hot-state), а суб-агент тогда — оптимизация
  глубины, не костыль корректности.

## База + дельты

Этот шаблон + [[meta-vault/principles|principles]] — **база**. `principles.md`
проектного vault открывается словами *«следует базе + эти дельты»* и
перечисляет только отличия (например, учебный домен убирает `market/` — не
бизнес; творческий — оставляет). Новые проекты **рождаются из этого шаблона**
и потому корректны с первого дня, а не ретрофитятся.
